# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

C2S Setup Tool — a two-stage installer for configuring RHEL 8 workstations in the SRM IST Trichy VLSI Lab with EDA tools (Xilinx Vivado/Vitis, Cadence, Silvaco TCAD, CADRE VisualTCAD; Synopsys planned).

- `setup.sh` — a bash bootstrapper. Warns (doesn't block) about any of `CADENCE/ SILVACO/ XILINX/ SYNOPSYS/ CADRE/` missing next to it — none of them are required just to launch; a missing one only means that tool's install action isn't available yet, per-tool, at the point you actually try to use it (see below). Prompts for site config (lab name, hostname format, machine count) on first run, downloads the matching `c2s-setup-linux-amd64` release from GitHub with SHA256 verification (falls back to a cached local binary when offline), then `exec`s it with any arguments forwarded.
- The Rust binary (`src/`) — a Ratatui TUI that does the actual work: installing tool binaries, generating shell environments, provisioning lab users, and running diagnostics. This is almost always what you're editing. With no arguments it's the interactive TUI; with any flag (`--preinstall`, `--install cadence`, `--status`, ...) it runs headlessly instead — see "CLI mode" below.

## Commands

```bash
cargo build              # debug build
cargo build --release    # release build (this is what setup.sh downloads/runs)
cargo run                # run the TUI locally (most install actions need root — run under sudo)
cargo check               # fast type-check without codegen
```

There is no test suite (`cargo test` has nothing to run) and no lint config beyond rustc's default warnings — `cargo build` output is the correctness signal.

## Architecture

### Config and state

`src/installer/config.rs::LabConfig` is the one piece of state everything else reads. It's derived from a machine number (`sysadmin309{N}` / `srmist309{N}` / `vlsilab{N}.ist.srmtrichy.edu.in`) and persisted to `/var/log/vlsilab/install.state` as flat `KEY=VALUE` lines — phase completion flags (`XILINX=DONE`, `CADENCE_TIME=...`, etc.) and machine identity. If `VLSI_SITE_CONFIG` is set (passed by `setup.sh` after site setup), every state write is also mirrored to `$VLSI_SITE_CONFIG/machine_states/machine_{N}.state`, which is how a shared NFS/site directory aggregates state across the 20 lab workstations.

`get_root_dir()` resolves where `CADENCE/`, `XILINX/`, etc. live: it's `get_script_dir()`, which is **always `std::env::current_dir()` at call time, never persisted** — `setup.sh` validates those tool folders as direct children of wherever it's invoked from before it ever launches the TUI, and launches the TUI binary with that same `cwd`, so `get_root_dir()` must equal the *live* current directory, not a parent of it (it briefly climbed one level up in this repo's history, which broke every `get_tool_dir()` lookup) and not a *remembered* one either (it used to be written into `install.state` once on first run and read back from there forever after, so moving the installer + tool folders to a new drive/path kept resolving to wherever it happened to run the very first time — don't reintroduce persisting it). `MACHINE_NUMBER` and the phase-completion flags belong in `install.state` because they're durable settings; `SCRIPT_DIR` doesn't, because "where is this process running from right now" isn't one.

### TUI shell (`src/app.rs`, `src/main.rs`, `src/ui/layout.rs`)

Three-pane layout: Main Menu → Actions (sub-menu) → Details, plus a full-screen Log Stream view (`Focus` enum controls which pane has input focus). `App::handle_sub_menu_execute()` is the dispatcher for every menu action; `main.rs`'s event loop just routes key events into it or into one of the three modal input prompts (`InputMode`: machine number, add-user, custom-dependency).

**Every long-running action (installs, pre-install, dependency resolution, add-user) follows the same pattern**: set focus to `Focus::LogStream`, clone `log_tx` and the shared `busy: Arc<AtomicBool>`, `tokio::spawn` the async work, and only flip `busy` back to `false` **from inside the spawned task** once it actually finishes. Do not set `busy` to `false` right after calling `tokio::spawn` — that was the TUI bug fixed in this repo's history (the log view would flash "Task Complete" while the install was still running in the background). `App::on_tick()` watches for the `busy: true → false` edge and calls `refresh_users()` so background changes (new user, freshly-installed tool) show up without an explicit refresh action.

Progress and errors from spawned tasks reach the UI only through `log_tx: mpsc::UnboundedSender<String>` — there's no other channel back to `App` from a background task. `App::poll_logs()` drains it every frame.

`sys_validation.rs` and `network.rs` each run their own independent background scan (`spawn_system_validation` / `spawn_network_checks`) into an `Arc<Mutex<...>>` state the Dashboard/Network panes read directly; they're not gated by the `busy` flag since they're passive checks, not mutating actions.

### CLI mode (`src/cli.rs`)

`Cli::parse()` (clap derive) runs first in `main()`, before the terminal is ever touched — so `--help`/`--version` exit via clap before anything below matters. Immediately after, `ensure_root()` checks `users::get_effective_uid()` and, if not root, replaces the current process with `sudo <our own current_exe()> <our original args>` via `Command::exec()` (never returns on success — sudo takes over the inherited terminal for the password prompt from there, or fails cleanly if there's none). This is what makes running the raw binary directly (`./c2s-setup-linux-amd64`, skipping `setup.sh`'s own `sudo` check) still work instead of failing partway through the first privileged action. `Cli::wants_cli_mode()` is true if *any* flag was passed — that's the entire branch condition: no flags → TUI (raw mode, alternate screen, the usual `run_app` loop); any flag → `cli::run()` and exit, raw mode and the alternate screen never entered at all. This is what makes it safe to script over SSH — no TTY assumptions, no leftover terminal state to restore.

`cli::run()` calls the exact same `installer::tools::install_*` / `installer::launcher::recreate_env` / `installer::preinstall::run_preinstall` / `installer::dependency::resolve_and_install_dependency` / `user_mgr::create_or_configure_student_user` / `user_mgr::grant_env` / `user_mgr::grant_vnc` functions the TUI's `App::handle_sub_menu_execute()` (and `handle_grant_access_submit()`) call — there's no separate CLI-only implementation of any install or grant step, just a different caller wiring the same `log_tx` channel to `println!` instead of the log pane. `--install`/`--recreate-env` accept multiple tool names (repeated flag or comma-separated) and are validated against a fixed tool list *before* anything runs (`resolve_tool_names`), so a typo'd tool name three tools into a scripted run fails immediately instead of partway through. `setup.sh` forwards `"$@"` to the binary unconditionally, so `curl ... | sudo bash -s -- --preinstall --install cadence` works the same as running the binary directly.

### EDA environment generation (`src/installer/launcher.rs`, `src/installer/tools.rs`)

This is the part most tool-launch bugs come from, and it spans two generated files:

- `/opt/cadence/cadence-env.sh` — Cadence-only. Every `TOOL HOME` (LIBERATEHOME, CDSHOME, ASSURAHOME, QRC_HOME, PVSHOME, MMSIMHOME, IUSHOME, LECHOME, INNOVUSHOME, GENUSHOME, MODUSHOME, SSVHOME, JASPERHOME, MVSHOME, SIGRITYHOME, STRATUSHOME, PEGASUSHOME, XCELIUMHOME, EMXHOME, ULTRASIMHOME, VMANAGERHOME, INTEGRANDHOME, JLSHOME, SPBHOME) has to be defined here even if that sub-tool isn't installed yet — `_cds_add_path` silently no-ops on missing directories, but a *missing env var* breaks the tool's own launcher scripts. A home whose folder doesn't actually exist on disk should carry a trailing `#not found` comment (currently only `ULTRASIMHOME`/`LIBERATEHOME`) — that comment must be removed the moment the folder actually shows up under `/opt/cadence/`, and added the moment one goes stale; check `ls /opt/cadence/` against every line, don't trust the comment's history. Adding a new Cadence tool means adding its home dir here, not just a wrapper function in eda-launcher.sh — and don't assume the vendor's PATH subdirectory convention (`bin/`, `tools/bin/`, `tools.lnx86/bin/`) without checking; `QRC_HOME` was wired to a `tools/bin` that didn't contain the `quantus` binary at all for a while, silently making Quantus unreachable despite its home var being "defined."
- `/opt/vlsilab/eda-launcher.sh` — sourced by every user's `.bashrc` (injected by `user_mgr.rs::create_or_configure_student_user`). It stays cheap at shell startup: X11 display vars, the combined license server string, and Silvaco/CADRE PATH exports run unconditionally, but Xilinx and Cadence are lazy — `vivado`/`virtuoso`/etc. are wrapper functions that source the heavy environment (`settings64.sh` for Xilinx, `cadence-env.sh` for Cadence) on first call, then `unset -f` themselves so the real binary is used directly afterward. **Every Cadence binary needs a matching wrapper function here**: virtuoso, spectre, genus, innovus, modus, liberate, xrun, irun, tempus, voltus, lec, lec_auto, jg, assura, quantus, emx, pegasus-cpa, pegasus-lpa, pegasus-cmp, pegasus-caa — a tool home defined in cadence-env.sh with no wrapper here is unreachable from a fresh shell.

  **The wrapper function name must be the literal on-disk binary name, never the Cadence marketing/product name** — this repo's history got this wrong for exactly the tools whose CLI diverges from the product name, and it silently breaks in a way `cargo build` can't catch (it's just a string, no compiler checks it resolves to anything real). Concretely: Xcelium ships as `xrun`, not `xcelium`. Incisive ships as `irun`. Conformal ships as `lec`/`lec_auto`, not `conformal`. JasperGold ships as `jg`. Tempus and Voltus both live inside `SSVHOME`'s `bin/` (not their own `TEMPUSHOME`/`VOLTUSHOME` — there is no such folder). Pegasus has no single `pegasus` binary at all — it's four separate ones, `pegasus-cpa`/`pegasus-lpa`/`pegasus-cmp`/`pegasus-caa` (bash function names can contain hyphens, this is valid). Before adding or trusting any wrapper, verify with `find /opt/cadence/<TOOL_HOME_DIR> -iname <candidate-name>` against the real install tree — never from the product's marketing name alone.

`launcher.rs::recreate_env(tool, tx)` regenerates both files: for `"cadence"` it rewrites `cadence-env.sh`, then always calls `write_base_launcher()` to rewrite `eda-launcher.sh`. For `"xilinx"/"silvaco"/"cadre"` there's no separate per-tool file — those environments are fully inline in `eda-launcher.sh` — so `recreate_env` just refreshes the launcher. `sys_validation.rs`'s "Environment Script" status check mirrors this split: Cadence checks `CADENCE_ENV_FILE`, everything else checks `EDA_LAUNCHER`.

The repo root has untracked local copies of `cadence-env.sh` and `eda-launcher.sh` (not in git — they're deployed/reference copies, not source). When changing what `launcher.rs` generates, treat those files as the canonical target content to match, and keep them in sync manually if you update one side.

### Installing tool binaries (`src/installer/tools.rs`)

Cadence is structurally different from the other three tools: it isn't a single installer binary, it's delivered as one `.tar.gz` per sub-tool under `CADENCE/TOOLS/` (`ASSURA41.tar.gz`, `GENUS211.tar.gz`, `IC618.tar.gz`, ...). Every one of those archives, without exception, contains a top-level directory matching its own filename exactly — `tar xf NAME.tar.gz -C /opt/cadence/` produces `/opt/cadence/NAME/` on its own, no renaming needed. `install_cadence()` globs `CADENCE/TOOLS/*.tar.gz` and extracts each one directly; there's deliberately no hardcoded tool-name list, because there used to be one and it drifted out of sync with what's actually delivered more than once (it had `MODUS201`/`SIGRITY20211` when the real archives were `MODUS221`/`SIGRITY20221`, and `cadence-env.sh`'s `LIBERATEHOME` separately pointed at a never-delivered `LIBERATE201` until `LIBERATE217.tar.gz` actually showed up — always trust the filenames in `CADENCE/TOOLS/`, not a remembered list or a stale hardcoded `TOOL_HOME`). This mirrors the site's own hand-written `CADENCE/TOOLS/tools.sh`, which does the same `*.tar.gz` glob. Per-archive extraction is skipped if `/opt/cadence/<NAME>/` already exists, so dropping one new tool's archive into `TOOLS/` and re-running `--install cadence` only extracts what's new instead of re-extracting the entire (100+ GB) existing install; delete that tool's destination folder first to force a clean re-extract. `CADENCE/Analog_RHEL_8.tar.gz` and `CADENCE/Digital_RHEL_8.tar.gz` (at the `CADENCE/` root, not `TOOLS/`) are the bulk vendor-original combined bundles, and they *are* installed — in a first pass, before the `TOOLS/` glob. `tools.sh` doesn't touch them, but the per-tool tarballs alone leave a tool tree that's extracted-but-not-configured (this is what broke Virtuoso: no OpenAccess under `IC618/share/oa`), so the bundles go down first as the base layer and `TOOLS/` is extracted over the top as the authoritative copy.

Three rules keep the two passes from fighting, and all three matter:

- Bundles extract with `tar --skip-old-files`, so a bundle can only ever fill in what isn't already on disk — it never overwrites a file `TOOLS/` (or an earlier run) put there, whatever order things happen to run in.
- Every folder a bundle creates gets a `.c2s-from-bundle` marker file, and the `TOOLS/` pass treats a marked folder as overwritable (extract over it, then delete the marker) while still skipping an unmarked existing folder as already-installed. Without the marker the existing "skip if `/opt/cadence/<NAME>/` exists" check would make the bundles shadow every `TOOLS/` archive — the exact opposite of the intended precedence. The `.gtar` pass (JASPER) honours the same marker, but *removes* the marked folder first rather than extracting over it, since its payload is moved in entry by entry rather than unpacked by tar.
- Each bundle is stamped under `/opt/cadence/.c2s-bundles/<archive>.done` once extracted and skipped on later runs — these are 100+ GB archives. Delete the stamp to force a re-extract.

The bundles aren't shaped like the `TOOLS/` archives and can't be assumed to be: a `TOOLS/` archive always contains exactly one top-level folder named after itself, while a bundle may hold the tool folders at its top level *or* wrap them all in a single folder named after the archive. `bundle_strip_components()` sniffs a bounded prefix of `tar -tf` output (bailing as soon as it sees a second top-level entry, so it never streams the whole archive) and passes `--strip-components=1` only when everything sampled sits under one top-level folder matching the archive's own name. Don't replace that with a hardcoded strip depth.

JASPER is a special case within that: it's vendored as a doubly-wrapped archive (`JASPER2209.tar.gz.gtar`) whose filename doesn't match the `*.tar.gz` glob, and whose extraction produces a folder containing one more single-child folder before the real payload. `install_gtar_archives()` runs before the glob loop, finds every `*.gtar` file under `CADENCE/TOOLS/` (not hardcoded to JASPER by name — anything shipped the same way gets the same treatment), extracts it to a scratch dir *under the system temp dir* (never back onto the source media, which may be read-only/removable), unwraps however many redundant single-child folder levels wrap the payload (`unwrap_single_child_dirs` — not hardcoded to exactly two), and moves the payload's contents into `/opt/cadence/<NAME>/`, with `<NAME>` derived by stripping `.gtar`/`.tar.gz` off the archive's own filename.

**Every extraction pass ends with `link_openaccess()`.** Most CIC tools ship their own bundled, version-tagged OpenAccess install at their own top level — confirmed on this site: `ASSURA41/oa_v22.60.074`, `IC618/oa_v22.60.082`, `INNOVUS211/oa_v22.60.076`, `MODUS221/oa_v22.60.065`, `PVS222/oa_v22.60.076`, `QUANTUS212/oa_v22.60.072`, `SIGRITY20221/oa_v22.60.064`, `SPECTRE211/oa_v22.60.070`, `SSV211/oa_v22.60.087`, each 100+ MB and genuinely populated — but every tool actually *looks* for it at `<tool>/share/oa`, which the raw tar extraction only ever leaves as an empty placeholder directory. That's not a guess: it's exactly what Cadence's own `<tool>/share/oaInstallers/oaConfig` script does when you run it by hand (`createSymbolicLink "$OA_HOME" "$SHARE_ROOT/oa"`) — a documented "post-install configure step" (the tool's own missing-OA warning says so) that raw tar extraction skips entirely. Without it, tools warn about `$OA_HOME`/missing OA at best; Modus fails outright with a Tcl error trying to load its framework. `link_openaccess()` automates exactly that symlink for every tool that has its own `oa_v*` directory, and is conservative about it: it only ever replaces an empty placeholder or a symlink already pointing at some `oa_v*` (so re-extracting a tool at a different OA version stays current), and leaves a real, populated `share/oa` alone with a `[WARN]` rather than risk clobbering real vendor data some future archive might actually ship.

Adding a new Cadence sub-tool needs its `TOOL_HOME` added to `launcher.rs`'s `CADENCE_ENV_SCRIPT` *and* a wrapper function in `EDA_LAUNCHER_SCRIPT` — the extraction step itself needs no changes since it's filename-driven. `PEGASUSDFM221` is delivered and extracted like everything else, but note `DDI221`/`EMX20231` are shipped as `Base_*.sdp` payloads inside their archives (not a ready `bin/` tree like the others) — they get extracted to `/opt/cadence/` the same way, but may need an actual vendor install step afterward that hasn't been investigated or implemented; don't assume they're usable purely from being extracted.

`install_xilinx`/`install_silvaco`/`install_cadre` are still stubs: they only check the source directory exists, mark the phase done, and call `recreate_env` — they never invoke the vendor `.bin` installer (all three are delivered as self-extracting `.bin` files, structurally unlike Cadence's per-tool tarballs). Don't assume those tools get installed by running the TUI; only Cadence's extraction-based install is real right now. Every `install_*` function (Cadence included) must check its own source dir with `.exists()` and return `Err` if it's missing — `install_silvaco`/`install_cadre` didn't for a while and would silently `mark_phase_done` with nothing actually installed. This check now carries the *entire* weight of catching a missing tool folder: `setup.sh` only warns about missing folders, it doesn't block launch (see above), so an install action with no source dir present has to fail loudly here, not upstream.

### Per-user access grants (`user_mgr.rs`) — env and VNC are opt-in, not automatic

Pre-install only ever provisions the *one* student user `LabConfig` names for a machine (`srmist309N`). Everything past that — which real accounts on the machine get the EDA launcher sourced into their `.bashrc` ("env"), and which get a VNC session — is a separate, explicit choice the sysadmin makes per user, not something pre-install decides on anyone's behalf. This was a deliberate correction: an earlier version of this code auto-granted a persistent VNC session to the single config-derived student during pre-install, which doesn't fit a machine that may have several real accounts (a sysadmin's own login, guests, multiple students set up over time) where not all of them should get one.

`user_mgr::list_lab_users()` is the single source of truth for "which real accounts exist" — every UID-1000-to-59999 account from `getent passwd`, each with a best-effort `role` guess (`wheel` group or a `sysadmin`-prefixed name reads as Sysadmin, everything else as Student — display only, nothing is gated on it) and its current `bashrc_configured`/`vnc_configured` status. Both the Dashboard (`sys_validation.rs`) and User Management (`app.rs::refresh_users`) call this same function so they can't disagree about who exists or what they already have. The TUI's User Management screen lists all of them; "Grant Env/VNC to User" (`USERNAME[,env][,vnc]`, no flags = both) and the CLI's `--list-users`/`--grant-env`/`--grant-vnc` are the two ways to act on that list.

`grant_env()` is the same `.bashrc` injection `create_or_configure_student_user()` already did (that function now calls it), just usable standalone against an existing account instead of only right after creating one.

`grant_vnc()` sets up a *persistent* VNC session using `tigervnc-server`'s actual `vncsession`/systemd framework on RHEL8 (1.13+) — **not** the older "hand-copy `vncserver@.service` and edit it" approach most TigerVNC docs on the internet still describe; that package's own service file explicitly warns copying it to `/etc/systemd/system/` will fight the new one. The real mechanism: `/etc/tigervnc/vncserver.users` maps a display to a Linux username (`:1=srmist3091`), `vncserver-config-defaults` (shipped by the package, untouched here) already defaults new sessions to a GNOME desktop, and `systemctl enable --now vncserver@:N.service` starts it. `allocate_vnc_display()` reuses a user's existing mapping if they have one, otherwise picks the lowest unused `:N` (backfilling a gap left by a removed mapping, not just incrementing past the highest) — this is what turns the lab's `ssh -L 590N:localhost:590N user@host` + `vncviewer localhost:590N` pattern into a specific port per user (590 + N). Never opens the VNC port beyond localhost; the tunnel is the only intended path in, per the vendor unit file's own warning.

VNC auth is separate from the student's Linux login: the PAM config the package ships (`/etc/pam.d/tigervnc`) is for session setup (SELinux context, logind registration), not for authenticating the VNC connection itself, which still uses classic `vncauth` via `~/.vnc/passwd`. Since a grant can run fully unattended (`--grant-vnc` over SSH), `set_vnc_password()` generates a random password, feeds it to `vncpasswd -f` (the documented non-interactive form — one line on stdin, obfuscated bytes on stdout, never touches a file itself) as root, and writes the result into the target user's `~/.vnc/passwd` with the right ownership/permissions/SELinux context. **That password is logged once, in the grant's own output, and nowhere else** — there's no way to recover it after the fact short of granting again (which rotates it) or the user running `vncpasswd` themselves.

`grant_vnc()` also adds the target user to `edausers` (`groupadd -f` happens once in pre-install; membership happens per grant here). **As of now `edausers` still grants no filesystem permissions** — it's infrastructure for scoping a *specific* future permission (a scratch/log directory, a device node, etc.) to lab users via group membership instead of loosening things broadly (world-writable, or `/opt/cadence` itself group-writable). Do not `chgrp`/`chmod` a directory that contains actual tool binaries to be group-writable for `edausers` — that lets any member delete/replace a shared binary, accidentally or not; scope any grant to the specific scratch/cache path that actually needs it, or prefer redirecting the tool's writes elsewhere (most Cadence tools already fall back to a per-user writable path like `~/.cadence` on their own when their default log path isn't writable — that's usually enough without touching permissions at all).

### Not yet implemented

`docs/CLUSTER_TRACKER_ARCHITECTURE.md` describes a planned `vlsilab daemon` (systemd service, polls running processes via `sysinfo`, logs sessions/tool usage to a shared SQLite/Postgres `tracker.db` for sysadmin reporting across all 20 workstations). None of that exists in `src/` yet — it's a design doc for future work, not current behavior.
